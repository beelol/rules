# Report and publication contract

Use the [October 16 Core QA Site](https://monarch-core-qa-20261016-b17ff42.bilalitani4.chatgpt.site/) for report structure: a plain-language headline, exact run identity and revisions, overall verdict and counts, grouped expandable checks, search/filtering when useful, and captioned screenshots opening at full size. Do not copy its results, fixtures, dates, candidate, or count. Link each requirement to the runbook at the recorded playbook commit.

Begin with one complete sentence naming what users can do, the environment tested, and whether every required check passed. Follow with tier, candidate/version, build and playbook commits, fixture revision when used, organization, tester, UTC start/finish times, and evidence scope. Show failures first, then every required criterion. Each result must explain the user-facing feature, the exact requirement, what the tester did, the expected outcome, what happened, and which screenshot and record support it. Put raw IDs and detailed timing behind an expansion. Write captions as complete sentences. Label retries, accepted exceptions, and missing proof explicitly.

Preserve `PASS`, `FAIL`, `BLOCKED`, and `NOT RUN` in the restricted ledger. In the public report, show a binary `PASS`/`FAIL` release verdict for every required criterion when a binary presentation is requested: map `BLOCKED` and `NOT RUN` to `FAIL — not verified: <specific prerequisite or reason>` while retaining their native status and cause in the detail. An overall PASS requires every required criterion to pass on this candidate. An incomplete suite is not a completed passing run. A missing fixture is a verification failure, not proof that the product behavior is defective.

Prepare publication copies of screenshots and data. Remove credentials, tokens, cookies, customer data, returned private records, and unnecessary personal details. Label redactions; preserve unaltered originals in restricted storage. Public evidence must still visibly support its claim. Never publish the restricted fixture manifest.

Discover the current Sites tools and instructions. Create a separate report Site for a new candidate unless the user requests an update to an existing report. Publish it with public access and verify an unauthenticated visit. If Sites is unavailable, use a supported public artifact host when available and verify its anonymous access. If neither is available, preserve the complete local report and state the publication blocker without claiming a public link exists. Retain the Site/project/deployment identity and the evidence location for follow-up.
